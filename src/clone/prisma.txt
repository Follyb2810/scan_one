## 🧩 **1. Prisma Scalar Types (Basic Data Types)**

These map directly to the data types of your database.

| Prisma Type | Description                  | SQL Equivalent           |
|-------------|------------------------------|--------------------------|
| `String`    | Text values                  | `VARCHAR`, `TEXT`        |
| `Int`       | Integer numbers              | `INT`, `INTEGER`         |
| `Float`     | Decimal numbers              | `FLOAT`, `DOUBLE`        |
| `Boolean`   | `true` or `false`            | `BOOLEAN`, `TINYINT(1)`  |
| `DateTime`  | Dates and timestamps         | `DATETIME`, `TIMESTAMP`  |
| `Json`      | Any JSON value               | `JSON`                   |
| `Bytes`     | Binary data (like files)     | `BLOB`, `BYTEA`          |
| `BigInt`    | Very large integers          | `BIGINT`                 |
| `Decimal`   | High precision decimal       | `DECIMAL`                |

Example:

```prisma
model Product {
  id         Int      @id @default(autoincrement())
  name       String
  price      Float
  inStock    Boolean
  createdAt  DateTime @default(now())
}
```

---

## 🔗 **2. Prisma Relations (Foreign Keys / Associations)**

In Prisma, you can model relationships between tables just like you would in SQL — 1:1, 1:N, N:M.

### 🔸 a. One-to-Many (1:N)

One `User` has many `Post`s, but each `Post` has one `User`.

```prisma
model User {
  id    Int     @id @default(autoincrement())
  name  String
  posts Post[] // 👈 one-to-many
}

model Post {
  id       Int   @id @default(autoincrement())
  title    String
  content  String?
  authorId Int
  author   User  @relation(fields: [authorId], references: [id]) // 👈 many-to-one
}
```

> You must specify the foreign key (`authorId`) and link it using `@relation`.

---

### 🔸 b. One-to-One (1:1)

Each user has one profile:

```prisma
model User {
  id      Int     @id @default(autoincrement())
  name    String
  profile Profile?
}

model Profile {
  id     Int  @id @default(autoincrement())
  bio    String
  userId Int  @unique
  user   User @relation(fields: [userId], references: [id])
}
```

> Notice the `@unique` constraint for `userId` to make sure it's one-to-one.

---

### 🔸 c. Many-to-Many (N:M)

Users can like many posts, and posts can be liked by many users.

```prisma
model User {
  id      Int     @id @default(autoincrement())
  name    String
  likes   Post[]  @relation("UserLikes")
}

model Post {
  id      Int     @id @default(autoincrement())
  title   String
  likedBy User[]  @relation("UserLikes")
}
```

> Prisma will **automatically** create a join table for you! 💪

---

## 🛠 Bonus: Useful Field Attributes

| Attribute           | Description                              |
|---------------------|------------------------------------------|
| `@id`              | Marks the primary key                     |
| `@default(...)`    | Sets default values                       |
| `@unique`          | Ensures the field is unique               |
| `@relation(...)`   | Defines how tables are related            |
| `@updatedAt`       | Automatically updates timestamp on change |
| `@map("colName")`  | Maps Prisma field to DB column name       |

Yes, **you absolutely can use Prisma with MongoDB!** 🎉

While Prisma was originally built with **relational databases** in mind (like PostgreSQL and MySQL), it now fully supports **MongoDB** as well — with some slight differences in modeling and features.

---

## 🧩 Key Differences Using Prisma with MongoDB

### ✅ Supported:
- ✅ **CRUD operations**
- ✅ **Relations** (embedded documents or references)
- ✅ **Filters, pagination, sorting**
- ✅ **Enum**
- ✅ **Migrations** using `prisma db push` (not traditional migrations)

### 🚫 Not Supported Yet:
- ❌ SQL-style joins (Mongo doesn’t support that natively)
- ❌ Some advanced SQL-only aggregations (MongoDB has its own aggregation pipeline)

---

## 🔌 Example MongoDB Prisma Schema

```prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "mongodb"
  url      = env("DATABASE_URL")
}

model User {
  id        String   @id @default(auto()) @map("_id") // Mongo uses ObjectId
  email     String   @unique

  gender    Gender

model Post {
  id        String   @id @default(auto()) @map("_id")
  title     String

  userId    String

  FEMALE
}
```

## 🛠️ Scenario: Users and Posts

- A **User** has many **Posts**.
- A **Post** belongs to one **User**.

---

### 🧾 1. Prisma Schema Setup (`schema.prisma`)

```prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "mongodb"
  url      = env("DATABASE_URL")
}

model User {
  id      String  @id @default(auto()) @map("_id")
  name    String
  email   String  @unique
  gender  Gender
  posts   Post[]  @relation(fields: [id], references: [authorId])
}

model Post {
  id        String   @id @default(auto()) @map("_id")
  title     String
  content   String?
  authorId  String
  author    User     @relation(fields: [authorId], references: [id])
}

enum Gender {
  MALE
  FEMALE
}
```

### 📌 Notes:

- MongoDB uses `_id` internally; we map Prisma’s `id` to it with `@map("_id")`.
- Relations use manual linking via ObjectIds (`authorId`).
- Prisma simulates relationships — it's not enforced by MongoDB itself.

Great! Let's dive into **validation in Prisma** — especially with enums, required fields, default values, string lengths, and more. Prisma gives us **schema-level validation**, and you can combine that with **application-level validation** (e.g., using Zod or Joi in your routes).

---

## ✅ Prisma Schema Validations

### 1. **Enum Validation** (e.g., gender)

```prisma
enum Gender {
  MALE
  FEMALE
}

model User {
  id     String  @id @default(auto()) @map("_id")
  name   String
  email  String  @unique
  gender Gender  // only accepts MALE or FEMALE
}
```

In this case, Prisma will **only allow `MALE` or `FEMALE`** as values.

---

### 2. **Required Fields**

By default, Prisma fields are required unless marked with `?`.

```prisma
model User {
  id       String @id @default(auto()) @map("_id")
  name     String     // required
  email    String     // required
  age      Int?       // optional
  bio      String?    // optional
}
```

If you try to insert a user without `name` or `email`, Prisma will throw a validation error.

---

### 3. **Default Values**

```prisma
model User {
  id        String  @id @default(auto()) @map("_id")
  name      String
  isActive  Boolean @default(true)
  role      String  @default("user")
}
```

If you omit `isActive` or `role` during creation, the default will apply.

---

### 4. **String Length & Constraints**

Prisma **does not** enforce string length in schema (like `VARCHAR(255)` in SQL), but **you should use app-level validation** (like Zod or class-validator).

For example, in a Next.js API:

```ts
import { z } from "zod"

const userSchema = z.object({
  name: z.string().min(3).max(100),
  email: z.string().email(),
  gender: z.enum(["MALE", "FEMALE"]),
})

const body = await req.json()
const result = userSchema.safeParse(body)

if (!result.success) {
  return Response.json({ error: result.error }, { status: 400 })
}

// Now safely create the user using Prisma
await prisma.user.create({ data: result.data })
```

---

### 5. **Unique Constraint**

```prisma
model User {
  id     String @id @default(auto()) @map("_id")
  email  String @unique  // ensures no duplicate email
}
```

If you try to create a user with the same email, Prisma throws an error like:
> Unique constraint failed on the fields: (`email`)

---

### 6. **@updatedAt & @default(now())**

```prisma
model Post {
  id        String   @id @default(auto()) @map("_id")
  title     String
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}
```

Prisma will auto-generate the date fields for you.

Use a validator library like:
